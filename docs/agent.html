Running an AI agent on real systems

Most of the code in my lab is written by Claude Code, working in a container next to the systems it changes. Getting good work out of it turned out to be less about prompts and more about context, runbooks, checks that run by themselves, and a clear line around what it may do alone.

AgentClaude Code, own container
PrivilegesNo sudo; risky steps go to me
ContextCLAUDE.md, skills, memory files
ChecksHooks after every edit

Where the line is

The agent runs as a normal user with no sudo in its own unprivileged container. It edits a git repo that mirrors the machines' live config and deploys routine changes over SSH through a runbook: back up, copy, restart, verify. Every command it runs passes Claude Code's permission mode first, which lets routine work through and stops riskier steps, like changes to a host itself or restarting services outside the web app. When a step is stopped, the agent doesn't retry it or look for a way around. It gives me one copyable block of commands for the host shell, I read it and run it, and the agent then checks the result read-only. The risky changes pass through me before they happen, and the agent still does the legwork.

Context: the rules file

Every session loads a CLAUDE.md at the repo root. Mine is short, and each rule is there because something went wrong once without it:

  • Pull first. The hosts push their live config to the repo every hour, so the agent's checkout goes stale between sessions.
  • Live wins. The repo mirrors live files, and the next sync overwrites repo edits that weren't deployed. An edit isn't done until it's deployed and the sync confirms it.
  • Back up before overwriting, verify after. A tarball on the target, named for the change.
  • Never deploy redacted files. Some configs reach git with their secrets stripped; copying those back would break the service.
  • Secrets never go in git; security changes go in a log kept outside it.

It also carries the defaults I'd otherwise repeat every week: dark themes, 24-hour clocks, one time zone on every machine, and "anything that needs a person goes on the health page". A sanitized excerpt is in the repo.

Skills as runbooks

A skill is a markdown file the agent loads when a task matches it. I use them as runbooks for anything done more than twice:

  • deploy: pull, map each repo path to its machine and live path, lint, back up, copy, restart, verify, restore the backup if it's broken. It also holds the gotchas ("these nginx sites are symlinks, copy to sites-available").
  • save-note: plans and to-dos go into plain markdown files in my notes folder, in a fixed format, so they outlive the chat.
  • handoff: before starting a fresh session, work out what the next session would be missing and write only that, in the right place (memory, the rules file, the plan note, or a short handoff note).

Runbooks make the agent consistent across sessions, and they're easy to fix. When a deploy goes wrong in a new way, the fix goes into the skill, and every later session has it. A generic deploy skill is in the repo.

Hooks: checks the agent can't skip

Instructions can be forgotten in a long session. Hooks run anyway.

HookWhenWhat it does
LintAfter every file editRuns ruff with only the rules that catch real bugs (undefined names, unused variables, syntax). Findings exit with code 2, which feeds them straight back to the agent, so it fixes the bug in the same turn. Silent otherwise.
Request queueSession startShows requests I dictated on my phone. The agent mentions them and asks which to do; it doesn't act on them unasked.
Sign-offWhen I say "goodnight" or "taking a break"Reminds the agent to wrap up first: save what it learned, commit and push, tell me what's still open. It ignores the phrase when it means something else ("make a goodnight scene").

r = subprocess.run([ruff, "check", "--quiet", "--select", "F821,F811,F841,E9,PLE", path], ...)
if r.returncode == 1 and r.stdout.strip():
    print(f"ruff found likely bugs in {path}:\n{r.stdout.strip()}", file=sys.stderr)
    sys.exit(2)                       # exit 2: Claude Code shows stderr to the agent

Memory

The agent keeps a memory folder: one fact per markdown file, each with a type (who I am, feedback on how to work, project state, pointers to outside resources) and a one-line description. An index file with one line per memory loads at the start of every session; the agent opens the full file when it's relevant. Feedback memories say why and how to apply the rule, so the agent can tell when it doesn't apply. Dates are always absolute ("2026-11-03", never "last Tuesday"), and the folder is copied to the NAS when a session wraps up.

The habit that made the biggest difference is a fresh session per topic. Long sessions get worse and cost more, so when a topic changes I run the handoff skill and start clean.

What broke

A "read-only" script deleted five files

The agent wrote a PowerShell scan for my desktop that was meant to only read files. It defined a helper called rd to read them. In PowerShell, rd is a built-in alias for Remove-Item, and aliases win over functions, so every call deleted the file. The script also set $ErrorActionPreference = 'SilentlyContinue', which hid what was happening until five files were gone.

What changed: a memory rule (never name helpers after built-in aliases; read through .NET calls like [IO.File]::ReadAllText; don't silence errors on a first run), which the agent now applies to every Windows script it writes. The memory file is in the repo as an example of the format.

A temporary root key that came back

Moving the agent's container between hosts needed a temporary root SSH key from one host to the other. It was left behind after the move, found a day later, removed, and logged. A week after that it was back. On Proxmox, /root/.ssh/authorized_keys is a symlink into the cluster filesystem, and a package upgrade most likely recreated the link and merged the old lines back in.

What changed: any temporary key, token or firewall opening gets its removal step written into the same runbook that creates it, and the job isn't done until that step is ticked. And after removing a key, check the real file behind the symlink, not just the path through it.

What I'd tell someone starting

  • Write the rules down where the agent reads them every time, and keep them short enough that it does.
  • Turn every repeated procedure into a runbook, and fix the runbook when it fails, not just the incident.
  • Put checks in hooks, not in instructions.
  • Keep a person on the risky steps, and make the hand-off cheap: one block to read and paste. It's slower by a minute, and it means I know what changed.
  • Make it say what it verified, and what it didn't.
